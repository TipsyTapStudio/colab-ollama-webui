# 2026-08-10 フェーズ3: Drive 永続化を実装

フェーズ1達成を受けて、PRD 4章の永続化方式（起動時復元 / 稼働中の定期バックアップ /
停止時の書き戻し）をノートブックに実装した。実機検証はこれから。

## 設計判断

- **セル2（Drive マウント＋復元）は序盤に置いた。** `drive.mount()` はユーザーの許可クリックで
  ブロックするため、「すべてのセルを実行」の直後1分以内に操作が来るようにする。
  長いインストールの後ろに置くと、許可待ちで放置される
- **復元は「ローカルに webui.db が無いときだけ」実行。** 同一ランタイムでの再実行時に、
  空の（あるいは古い）Drive 側でローカルの最新データを上書きしないため。
  ダーティなランタイムでの再実行を常に安全側に倒す
- **SQLite のバックアップは Python 標準の `sqlite3` オンラインバックアップ API で
  ローカルにスナップショット → Drive へ通常コピー。** 稼働中の DB を素朴に rsync すると
  書き込みと重なって壊れたコピーになりうる（定期バックアップは「予期せぬセッション切断」への
  保険なので、その瞬間のコピーが壊れていては意味がない）。また Drive(FUSE) 上のファイルを
  SQLite で直接開かない（リスク2の回避を書き戻し側でも徹底）
- **webui.db 以外は rsync -a --delete**（`cache/` は除外）。`--delete` があっても
  `--exclude` 対象は削除されないので、別経路でコピーする webui.db とは干渉しない
- **定期バックアップはカーネル内の daemon スレッド**（5分間隔、`/content/sync.log` に記録）。
  カーネルが死ぬとスレッドも死ぬが、それは保険が薄くなるだけで、主経路（停止セル）と
  次善（直近5分以内のバックアップ）は残る。プロセス分離は複雑さに見合わないと判断
- **停止セルの順序**: cloudflared / Open WebUI を止める → 5秒待つ → 最終バックアップ →
  Ollama を止める。DB への書き込みが止まった静止状態で書き戻すため（ここが主たる保存経路）
- **リスク5の設定も自然に永続化される。** サインアップ無効化は webui.db 内の設定なので、
  履歴と一緒に Drive へ乗る。2回目以降は前回のアカウントでログインするだけ

## 検証手順（次回）

1. 稼働中のランタイムで新ノートブックを再実行 → Drive マウント＋バックアップ開始
   （ローカル優先の復元スキップが働くこと）
2. 停止セル（STOP チェック）→「履歴を Drive へ書き戻した」が出ること（AC4）
3. ランタイム削除 → 再実行 → 前回のアカウントでログインでき、チャット一覧に履歴が
   残っていて続きから話せること（**AC3 = 本丸**）
